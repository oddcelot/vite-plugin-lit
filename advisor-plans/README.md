### Direction — options for the maintainer, not defects

1. **Type the public timeline API.** `README.md:147-168` documents
   `import {addTimelineEvent, addTimelineLayer} from 'virtual:lit-plugin/timeline'`
   as a supported extension point for app code and other plugins, but
   `client.d.ts` declares only the two CSS queries and `package.json`'s `exports`
   has no entry for the runtime's `timeline/public-api`. A TypeScript consumer who
   follows the README gets `TS2307: Cannot find module`. Adding the ambient
   declaration is an afternoon; it turns a documented feature from "works if you
   silence the compiler" into a real public API. Trade-off: it freezes the
   virtual module's shape as public surface.

2. **Surface HMR-incompatibility diagnostics in the panel.** The plugin already
   detects precisely why a component cannot be hot-patched — standard `accessor`
   decorators, `#private` fields, changed `observedAttributes` — and routes each
   through `incompatible(state, tagName, reason)` at
   `src/lib/runtime/patch.ts:268-283`, which today only writes to the console
   before reloading. `README.md:364-386` documents these as the product's known
   limitations. The DevTools panel, its SSE transport, and the settings channel
   already exist, so piping those reasons into a "why did this reload?" list is
   mostly wiring. It converts the package's most confusing failure mode into its
   most legible feature. Trade-off: more surface in a panel that already has
   three tabs.

3. **Run the lit-canary suite on a schedule.** The repo carries the lit monorepo
   as a submodule and a full opt-in canary path (`scripts/build-lit-canary.mjs`,
   `LIT_CANARY=1`, `src/test/canary.ts`, documented at `README.md:450-465`) whose
   entire value is early warning when lit `main` breaks in-place patching — the
   thing that most distinguishes this fork. Nothing runs it automatically. A
   weekly scheduled CI job (after plan 002 lands) is the cheapest way to make that
   investment pay. Trade-off: a scheduled job that fails for upstream reasons
   needs an owner, or it becomes noise.

## Findings considered and rejected

- **Unbounded `byContent` intern map** (`src/lib/runtime/intern.ts:23-42`): two
  audit passes flagged it as a memory leak, but `README.md:381-384` documents it
  as a known, accepted limitation ("bounded by the number of edits and cleared by
  any full reload"). Dev-only, bounded by edit count, and the fix would add an
  eviction path that can cost an extra template rebuild. Not worth doing as a bug;
  revisit only if someone reports real memory pressure in a long session.
- **`launch-editor`'s Windows `cmd.exe` quoting doesn't escape `"`**: a
  dependency-level gap with no reachable path here — the middleware only accepts
  paths to files that already exist under the allowed roots, so an attacker cannot
  introduce a filename containing a quote. Track upstream if ever relevant.
- **Design-system modules (`tokens.ts`, `segmented-tabs.ts`, `icons.ts`,
  `color-scheme.ts`) living in `src/lib/` next to Node-side plugin code**: no
  layering violation — they import only `lit`, and both browser surfaces (injected
  overlay and the panel app) need them. A move would touch every import site for
  zero behavioral gain.
- **`engines.node >=20` vs `devEngines.runtime node >=26`**: not a contradiction.
  `engines` is the consumer requirement for the published ES2022 output;
  `devEngines` is what this repo's toolchain needs. At most, a comment naming
  which tool forces Node 26.
- **`optimizeDeps.exclude` being a no-op causing duplicate module instances**: the
  stale specifier is real (plan 005), but the feared consequence is not —
  `src/lib/runtime/css.ts` holds no module-level state, so a prebundled copy would
  not split a cache. Plan 005 treats it as dead code and documentation, not a
  runtime bug.

## What was not audited

- The `lit/` submodule (upstream lit monorepo, `update = none`) and
  `node_modules/` — out of scope by design.
- Generated build output at the repo root (`lib/`, `types/`, `panel/`,
  `index.js`, `index.d.ts`) — regenerated from `src/` by `pnpm run build`.
- `bench/` was read for context (what is already measured) but not audited for
  correctness, and `playground/` was treated as fixture code, not product code.
- No test suite was executed during the audit — the advisor is read-only and the
  e2e suite mutates the working tree. Every plan's verification commands were
  taken from `package.json` / `vite.config.ts` and, where behavior mattered
  (`vp check --help`), confirmed with a read-only invocation.
